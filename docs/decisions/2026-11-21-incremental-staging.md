# Incremental staging and the crash-safe swap (#72)

- **Question:** how does `nvmod stage` change one Mod's files without building the whole tree, and stay safe when it stops half way?
- **Decision:** a run is incremental when the manifest of the last run has the current layout (schema 2), was built the same way (`--copy`, the protected globs) and has a record for every file; otherwise, or with `--full`, the whole tree is built beside the old one and swapped in. An incremental run compares the plan with the records (and the tree with its records, so a path a program changed is put right too) and does link, unlink and replace operations; the report says `mode` and `operations`. The operations are listed in `staging/<profile>.ops.json` before the first runs, and a file an operation removes or replaces is moved to `staging/<profile>.trash/<n>` first. Deleting the journal is the commit. A run that stops before it is undone by the next `nvmod stage` (the Doctor reports `stage.interrupted` until then): the moved files go back and what the operations made is removed, which is the old tree. A failure inside a run undoes it at once (exit 4). The manifest is written through a temporary file and a rename. The file times of the plugins are set after the operations, as in a full build.
- **Why:** the old tree stays complete until the commit, so after a stop the tree is the old one (after the next run's undo) or the new one, never a mix a person has to repair; leaving the manifest older than the tree after a stop between the commit and the manifest write only makes the next run repeat a few operations. Comparing the tree with its records keeps the result equal to a full build.
- **Revisit:** the Instance lock of the executables registry is taken by the commands that stage (the lock module), not by the library call; a Toolbox that calls `nvmod_stage::stage` itself while another run stages needs its own lock.
