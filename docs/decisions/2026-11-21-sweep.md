# Sweep: what a program did to the Staging tree (#75)

- **Question:** how does program output get from the hard-link Staging tree back into the Instance, as Overwrite does under Mod Organizer?
- **Decision:** the manifest of a built tree (schema 2) holds a record per file: provider, the provider's spelling of the path, file id (inode or file index), size, modification time and link count. `nvmod sweep` compares the tree with it. A path with no record is `new`; a path whose file id changed, or whose content changed while the record was a copy, is `replaced`; both move to `overwrite/` (or to the Mod named with `--to`), spelled as the providers spell existing folders, and an earlier file at the destination goes to the trash. A path that changed through the shared file id is `modified-in-place` (the Mod's own file changed, as under Mod Organizer) and is only reported. A path that is gone is `deleted-by-program` and only reported. The tree is then built again, which puts every provider's file back and shows Overwrite on top. `--protect <glob>` appends a glob to `<profile>/nvmod-protect.txt`; the next tree stages matching paths as copies. The Doctor reports `stage.unswept` while the tree differs from its records. The sweep is a lifecycle action with a journal of kind `sweep`.
- **Why:** moving only what is new or replaced is safe to repeat: an interrupted sweep leaves each file in the tree or in Overwrite, and the next run finishes it, so `nvmod rollback` skips a sweep journal (a rollback would build the tree again and drop what the program wrote). Rebuilding the tree restores links without a separate repair step. Reporting in-place writes instead of undoing them matches Mod Organizer.
- **Revisit:** the per-executable target (`custom_overwrites/<exe>` of Mod Organizer's `settings.ini`) and paths outside `Data` (extender logs) are not covered yet; check when the Toolbox calls the sweep after a run.
