## First run on the real instance

The doctor was run read only (headers only; no file written, nothing executed) against the owner's instance on
2026-11-14: 47 plugin DLLs in the merged view of the `TTW Wasteland Survival Guide` profile, 41 in the catalogue,
0 errors. It found the known `MAC-TEN` mismatch (`meta.ini` says Nexus id 10, the checklist says 83815), saw the
executable as 4GB-patched with a backup present and `nvse_steam_loader.dll` imported (so no loader executable is
needed to start xNVSE), and showed that **every real plugin declares itself through `NVSEPlugin_Query` only**: none
exports `NVSEPlugin_Version`. That is why the doctor does not raise a finding for the legacy interface.

## Unverified assumptions

These are in the code as named constants or comments and in findings as lower certainty. Each is a spike to close
against the real xNVSE source and a real `nvse.log`.

1. **Version struct layout.** The doctor treats the export `NVSEPlugin_Version` as a data symbol that starts with two
   little-endian `u32`: `infoVersion` and `version`. Nothing after them is read. The layout is from memory (plan
   spike S2). The finding says so.
2. **Which exports make an NVSE plugin.** `NVSEPlugin_Query`, `NVSEPlugin_Load` and `NVSEPlugin_Version` (plan
   section 6.1, also from memory). A DLL with none of them is reported as "not an NVSE plugin", which can be right
   for a helper library placed in the plugin folder.
3. **Supported game executable.** `1.4.0.525` (plan section 6.1 item 2).
4. **Runtime DLL names** treated as "needs the Visual C++ runtime in the prefix": `msvcp*`, `vcruntime*`, `concrt*`
   (versions 100 and up; `msvcr*` of the 2010 and earlier runtimes is reported as a runtime too).

Storefront markers: `.egstore` is Epic, `goggame-1454587428.info` or `goglog.ini` is GOG, `steam_api.dll` is Steam; Epic and unrecognised copies are refused (exit 2) with a reason. | Load order | `nvmod sort --instance <dir> [--profile <name>] --masterlist <file> [--apply] [--json]` builds the plugin list from the profile's `loadorder.txt` (order) and `plugins.txt` (active) and calls `loot_rs::api::sort` with the `Data` folder of the Staging tree (no tree: exit 2 and the `nvmod stage` command). loot-rs is linked as a library, a git dependency pinned to the tag `v0.2.0` (ADR-0003; `allow-git` in `deny.toml` names only that repository; the licences are GPL-3.0-only on both sides). Without `--apply` it prints the proposal and the LOOT messages and writes nothing. `--apply` writes `plugins.txt` (active plugins, Windows code page) and `loadorder.txt` together after a journal and backup of the profile files, so `nvmod rollback` undoes it (journal kind `sort`: it restores the two lists and rebuilds the Staging tree, and never touches a Mod folder or `modlist.txt`); a step that fails restores them and exits 4 (`NVMOD_FAIL_AT=sort-lists\|sort-times` injects one). A plugin that is not installed (loot-rs leaves it out) is placed right after the plugin that preceded it in the current order (`SortOutput::order_with_not_installed`). Plugin file times: plugin number `n` of the Load order gets `1_000_000_000 + 60 n` seconds since the epoch (strictly increasing, the same for the same order), because nv-rs orders by file time until the fork has a `plugins.txt` switch. The Staging tree hard-links plugin files to the Mod folders (and to the base copy), so each plugin file whose inode is shared is first replaced by a copy and only then stamped: no Mod, base-copy or MO2 file is touched. Running `--apply` twice changes nothing the second time (no journal, no write). A name the Windows code page lacks, or rules that contradict each other, refuse before any change. The Doctor on an Instance (`nvmod doctor --instance <dir> [--masterlist <file>] [--catalog <file>]`) reports `loadorder.missing-master` (error: an active plugin's master is absent, inactive or later), `loadorder.differs-from-loot` (warning with a masterlist, info without: only header masters and the current order then decide), `loadorder.times-out-of-order` (warning: a rebuilt Staging tree loses the times; `sort --apply` rewrites them) and, for NVSE plugin DLLs of the Staging tree, `plugin.game-version-mismatch` and `plugin.xnvse-version-mismatch` against the catalogue's new optional `game_version` and `min_xnvse` fields. A field the catalogue does not record is reported as `plugin.requirements-unknown` (info) and never guessed; the shipped catalogue records none yet. The Doctor compares the required values with the base copy's executable version and the file version of `nvse_1_4.dll` in the base copy, not with anything read from the plugin DLL, whose version struct is still an unverified assumption (see below) | Ticket 19 of nv-linux. The authoritative order is the one in the profile; the times are a derived cache that a rebuilt tree loses |
| Cancel scope (#212) | Every `nvmod_api` job runs its safe points (`step_point`, the install copy, the lists, the profile transaction, the backup steps) under its own `CancelToken` and ignores the process-wide stop request (`nvmod_core::cancel::enter`, a per-thread scope the job holds). ## 2026-11-20: the downloads library (nvmod-rs #78)

| Question | Decision | Why | Revisit |
| --- | --- | --- | --- |
| Where it lives | A library crate `nvmod-downloads` (reading, matching, hashing, the `.meta` edits and the trash move) and the typed jobs `downloads::list`, `show`, `install` and `change` (hide, unhide, forget) in `nvmod-api`, which the Toolbox calls in process; `nvmod downloads list\|show\|install\|hide\|unhide\|forget` wrap the jobs | The Toolbox's Mods page reads the library through the job API, not the command line | No |
| Folder | `<Instance>/downloads`, or the folder a request names (`--downloads`; a relative path is read from the Instance folder). The Instance file stores no downloads path, so the caller passes MO2's `download_directory` when it differs. A missing default folder is an empty library; a named one that is missing is refused | `nvmod-instance.json` stays at schema 2 | When an import should record the folder |
| What is an archive | Every regular file of the folder (not the subfolders) except `*.meta`, dot files and `*.nvmod-tmp`. An orphan `.meta` is not listed. Names that are not UTF-8 are skipped | MO2 lists the folder's files and keeps its state in `<archive>.meta` | No |
| `.meta` keys | Read as MO2 writes them: `gameName`, `modID`, `fileID`, `name`, `modName`, `version`, `newestVersion`, `repository`, and the state keys `installed`, `uninstalled`, `paused` and `removed` (MO2's hide). Nothing is re-serialised: a write edits only its own line with the line-preserving `MetaIni` (a key that is missing is added at the end of `[General]`), so a file where only `installed` changes comes back byte for byte. `url` and `userData` are never printed | MO2 and nvmod share the file | No |
| State | `hidden` (`removed=true`), else `paused` (`paused=true` or a name ending `.unfinished`), else `installed` (a Mod's `installationFile` names the archive, compared without regard to case, or the `.meta` says `installed=true` and not `uninstalled=true`), else `uninstalled` | The four states of the ticket, in MO2's order of precedence | No |
| Ids and match | The Nexus mod id is `modID` of the `.meta`, else the Nexus file name pattern (`parse_nexus_name`), with `id_source` saying which; the file id is only from the `.meta`. The matched Mod is the first (by folder name) whose `installationFile` is the archive (`installation-file`), else the first with the same mod id (`mod-id`, another file of the same Nexus mod; it does not make the archive `installed`) | A name pattern can be read wrongly, so the source is shown | No |
| `--unmatched` | Archives that match no Mod, and Mods whose `installationFile` is absent or not in the folder (`mods_without_archive`, empty without the flag). Separators are not Mods | The ticket | No |
| Output | `--json` has `schemas/downloads-list.v1.json` and `schemas/downloads-show.v1.json`, checked against the Rust types by a test. `installationFile` is read through `file_name_only`, so no output holds a directory or a Windows path; the job refuses a file name with `/`, `\`, `:` or a control character and a name ending `.meta` | A path in an archive name could reach outside the folder | No |
| Install | `downloads install <archive>` is `install::install` on `<downloads>/<archive>` (the same profile, name, answers, limits, dry run and FOMOD questions), then, only when a Mod was installed and it was not a dry run, the `.meta` marked `installed=true` (and `uninstalled=false` when it was true; a missing `.meta` is made with `[General]` and `installed=true`). A `.meta` that cannot be written is a warning in the result; the Mod stays installed. A paused download is refused. The install is journaled as before, so `nvmod rollback` removes the Mod but does not touch the `.meta` | One install path | When a rollback should unmark the archive |
| Hide, unhide, forget | Hide and unhide edit only `removed` (a missing `.meta` is made for a hide; nothing is written when the state is already as asked). Forget moves the archive and its `.meta` to `.nvmod/trash/downloads/<millis>-<pid>/` (a copy then a remove when the folders are on different volumes); nothing is deleted. These take the Instance lock; `--dry-run` writes nothing | A download is the owner's data | No |
| Hashes | `--hash` adds MD5 and SHA-256 (`sha2`, already locked, and `md-5` 0.11.0, which uses the same `digest`). Each file is read once for both, in 1 MiB blocks, with the cancel token checked between blocks. The cache `.nvmod/downloads-hashes.json` is keyed by file name, size and modification time; it is a convenience (it can be deleted, and a write failure is ignored), pruned to the folder's files by `list` | MO2 and Nexus use MD5, release notes use SHA-256 | No |
| Cost | Without `--hash` a listing reads each `.meta` and the folder once; 2000 archives with 1000 `.meta` files list in well under a second on the test machine. A test bounds it at 10 s so a loaded CI machine does not fail it | The ticket asks for under 2 s | No |
| No network, no process | The library and the jobs open files only | ADR: nvmod starts no process | No |

## Archive extraction limits (#81)

| Decision | Choice | Why |
| --- | --- | --- |
| Paths | Refused: absolute, drive letter, UNC (`\\server`, a leading separator), `..`, a `:` (alternate data stream), control characters, Windows device names (`CON`, `COM1`, ...), a name ending in a dot or a space (Windows drops it). Both `/` and `\` separate folders. Symbolic links, hard links, devices and every other special entry are refused for zip, tar and 7z | A refused entry refuses the whole archive; the Mod folder is only ever written by plain files and folders |
| Collisions | Two files whose full paths differ only in letter case, a file named twice, and a name used as both a file and a folder (in any case) are refused. Folders that differ only in case (`Textures` beside `textures`, as real archives hold them) are accepted: nvmod stages lowercased paths and only two files can overwrite each other. A case-sensitive file system would keep both files and Windows or macOS would overwrite one with the other, so the result would depend on where it was installed | The game reads names without regard to case, so two such files have no single meaning |
| Writes stay inside | Each file is created with create-new (it never replaces a file and never follows a link at the target), and the canonical parent of every file and folder written is checked to lie inside the destination. No archive entry can create a link, so this guards against a link already in the folder | Defence in depth for the rule above |
| Limits and defaults | Total bytes 32 GiB (`--max-extract-bytes`), entries 500000 (`--max-extract-entries`), one file 8 GiB (`--max-extract-entry-bytes`), expansion 500 times the archive file's size (`--max-extract-ratio`), folders in a path 64 (`--max-extract-depth`), steps of work 4000000 (`--max-extract-operations`), time 1800 seconds (`--max-extract-seconds`). The constants are `DEFAULT_*` in `nvmod-modinstall::extract`; the library takes them through `Limits` or `LimitOverrides` (`InstallRequest.extract_limits`, `max_extract_bytes` kept) | Safe against a bomb, wide enough for a large real Mod (a 4 GiB BSA is one file) |
| Ratio | Checked only once more than 64 MiB (`Limits::ratio_floor_bytes`, not a flag) has been extracted, against the archive file's size, so a small repetitive file never trips it and a bomb stops at once past the floor. Declared sizes are checked before anything is written (zip, 7z); sizes read while copying are checked chunk by chunk (all formats), so headers that lie do not help | Highly compressible real data (a DDS of one colour) is small; a bomb is not |
| Steps and time | A step is an entry, a 64 KiB chunk of file data copied, or a read of tar metadata (headers, long names, pax records). The time limit is wall clock from the start of the extraction. Both end the extraction with a refusal | Bounds work that no byte limit bounds: millions of empty entries, a slow decoder |
| Nested archives | An archive inside an archive is never opened: it is written as one file and counts against the byte, ratio and time limits, so nesting depth is zero by construction. Folder nesting inside one archive is bounded by the depth limit | nvmod installs the files of one archive; opening inner ones would multiply every other limit |
| Refusal message | Names the limit and the flag that raises it, for example `... (limit --max-extract-ratio)`; the exit code is 2 and the Instance is untouched, because the scratch folder is deleted and nothing is placed until extraction ends | A person can tell what to change |
| Fuzzing | `fuzz/fuzz_targets/archive_extract.rs` feeds every in-process reader with tight limits (entries, bytes, ratio, depth, steps, time) and checks that nothing is written outside the destination; `archive_path` fuzzes the path check | The ticket asks for a target on the archive walker |
| Interactive FOMOD, saved answers, name clash | The FOMOD engine yields typed events (`nvmod_api::fomod::next`; `FomodEvent` is `{"event":"step",...}` with each group (id `step/group`, rule, min/max, decided or open) and option (description, image, type evaluated against flags and active Plugins, `dynamic`, `usable`, `selected`), or `{"event":"plan","files","inferred","answers"}`); schemas `schemas/fomod-events.v1.json` and `schemas/fomod-answers.v1.json` are generated and checked by tests. `nvmod install <archive> --interactive` prompts on the terminal (option numbers, empty line takes the ticked options, a bad line is asked again, end of input refuses with exit 2 and writes nothing). A FOMOD install writes `mods/<name>/.nvmod/fomod-answers.json` (`schema_version`, `module`, `archive`, `answers`); `nvmod mods reinstall <mod>` replays it, `nvmod mods reconfigure <mod> [--answers <file>\|--interactive]` asks again with the saved choices ticked. `--on-conflict replace\|merge\|rename` decides a name clash (default: refuse); replace keeps priority, enabled state, Plugin states and `meta.ini`. Scripted installers (BAIN `wizard.txt`, C# FOMOD) are still refused. No GUI or service code here | Ticket nvmod-rs#77, rauls-trusty-toolbox#395 consumes the stream. MO2 parity for the install dialog |
| Plugin file times follow the Load order at every staging (#223) | Building the Staging tree (`nvmod stage`, the stage inside `run`, and every command that stages again: `install`, `mods`, `rollback`, `backup restore`) sets the file times of the plugins listed in `loadorder.txt` (else `plugins.txt`) inside the new tree before it is swapped in, with the same rule and code as `sort --apply` (`nvmod_stage::stamp`: plugin `n` gets `1_000_000_000 + 60 n` seconds; a linked plugin is replaced by a copy first, so no Mod or base-copy file is touched). A profile with neither list is staged as before. A restage therefore never undoes a sort, and `sort --apply` right after a stage finds nothing to write. `nvmod run` plans a rebuild (reason: the plugin file times do not follow `loadorder.txt`) when the tree is otherwise current but its times are wrong, so the game does not start on the order of the Mod folders. `nvmod sort` without `--apply` no longer says "already sorted" for a tree whose times are wrong: it says the order is sorted but the times do not follow it, and `--json` has `times_stale`. A failure while stamping rolls the staging back like any other | The authoritative order is the profile's; the times are a cache that the game reads, so every writer of the tree must refresh it. Staging copies the plugin files (a few files), not the whole tree | No |
| Game guard (#227) | Every refusal "while the game runs" (`mods remove`, `backup restore`, `saves` restore, `profile apply`/`finish`) asks `nvmod_backup::game_running(<instance root>)`: the holder named in `.nvmod/lock` (the run hands the lock to the program it started) must be a live process other than the asking one. Process names (`FalloutNV.exe`, `nvse_loader.exe`, `nv-viewer`, `NVMOD_GAME_PROCESSES`) are no longer looked at; Mod Organizer 2 still is (by name, `NVMOD_PROC_DIR`) | A game of another Instance or of none must not block this one, and a game started as `raul --play-mode` (or any other name) must | No |
