now. Each was settled with the plan's recommendation as the default, and each entry says why. **Revisit** marks the
ones the owner should look at first, because they commit money, access, scope or someone else's repository.

## Implementation decisions

| Topic | Decision | Why |

| PE parser | Hand written (`nvmod-pe`), not `goblin` | The parser reads through a bounded reader, sizes no buffer from a header field beyond fixed limits and the file length, and never maps the whole file. It needs about ten fields. It is fuzzed. Approach taken from `loot-rs` `src/exe_version.rs` (read there, not copied: that code is for another purpose) |

| Merges | Squash only, auto-merge, branch deleted after merge | The owner's instruction; the PR title becomes the commit, so it must be a Conventional Commit |
| CodeQL | Default setup for `actions` and `python` | Rust is not offered by default setup. The Python in the repository is the guard script |
| Catalogue source | The DLL and INI names in `data/nvse-plugins.toml` were read from the file names in the owner's MO2 instance on 2026-11-14 (names only, nothing opened); Nexus ids come from the update checklist in NV-Linux-Modding. ## First run on the real instance

The doctor was run read only (headers only; no file written, nothing executed) against the owner's instance on
2026-11-14: 47 plugin DLLs in the merged view of the `TTW Wasteland Survival Guide` profile, 41 in the catalogue,
0 errors. It found the known `MAC-TEN` mismatch (`meta.ini` says Nexus id 10, the checklist says 83815), saw the
executable as 4GB-patched with a backup present and `nvse_steam_loader.dll` imported (so no loader executable is
needed to start xNVSE), and showed that **every real plugin declares itself through `NVSEPlugin_Query` only**: none
exports `NVSEPlugin_Version`. That is why the doctor does not raise a finding for the legacy interface.

## Unverified assumptions

These are in the code as named constants or comments and in findings as lower certainty. Each is a spike to close
against the real xNVSE source and a real `nvse.log`.

1. **Version struct layout.** The doctor treats the export `NVSEPlugin_Version` as a data symbol that starts with two
   little-endian `u32`: `infoVersion` and `version`. Nothing after them is read. The layout is from memory (plan
   spike S2). The finding says so.
2. **Which exports make an NVSE plugin.** `NVSEPlugin_Query`, `NVSEPlugin_Load` and `NVSEPlugin_Version` (plan
   section 6.1, also from memory). A DLL with none of them is reported as "not an NVSE plugin", which can be right
   for a helper library placed in the plugin folder.
3. **Supported game executable.** `1.4.0.525` (plan section 6.1 item 2).
4. **Runtime DLL names** treated as "needs the Visual C++ runtime in the prefix": `msvcp*`, `vcruntime*`, `concrt*`
   (versions 100 and up; `msvcr*` of the 2010 and earlier runtimes is reported as a runtime too).
| nvmod Instance and base copy | `nvmod init --base <dir> --instance <dir>` makes an Instance skeleton (`nvmod-instance.json`, `mods/`, `profiles/`) in a new folder outside the base copy, which is only read. `nvmod doctor --base <dir>` (or `--instance` on an nvmod Instance) checks the storefront, the executable and `Data`. Storefront markers: `.egstore` is Epic, `goggame-1454587428.info` or `goglog.ini` is GOG, `steam_api.dll` is Steam; Epic and unrecognised copies are refused (exit 2) with a reason. The markers are unverified against real copies | Ticket 14 of nv-linux. An executable other than 32-bit x86 version 1.4.0.525 is reported as `base.exe-unknown`; a 4GB-patched one of that version is accepted, as nv-rs accepts it |
| Load order | `nvmod sort --instance <dir> [--profile <name>] --masterlist <file> [--apply] [--json]` builds the plugin list from the profile's `loadorder.txt` (order) and `plugins.txt` (active) and calls `loot_rs::api::sort` with the `Data` folder of the Staging tree (no tree: exit 2 and the `nvmod stage` command). loot-rs is linked as a library, a git dependency pinned to the tag `v0.1.0` (ADR-0003; `allow-git` in `deny.toml` names only that repository; the licences are GPL-3.0-only on both sides). Without `--apply` it prints the proposal and the LOOT messages and writes nothing. `--apply` writes `plugins.txt` (active plugins, Windows code page) and `loadorder.txt` together after a journal and backup of the profile files, so `nvmod rollback` undoes it (journal kind `sort`: it restores the two lists and rebuilds the Staging tree, and never touches a Mod folder or `modlist.txt`); a step that fails restores them and exits 4 (`NVMOD_FAIL_AT=sort-lists\|sort-times` injects one). A plugin that is not installed (loot-rs leaves it out) is placed right after the plugin that preceded it in the current order. Plugin file times: plugin number `n` of the Load order gets `1_000_000_000 + 60 n` seconds since the epoch (strictly increasing, the same for the same order), because nv-rs orders by file time until the fork has a `plugins.txt` switch. The Staging tree hard-links plugin files to the Mod folders (and to the base copy), so each plugin file whose inode is shared is first replaced by a copy and only then stamped: no Mod, base-copy or MO2 file is touched. Running `--apply` twice changes nothing the second time (no journal, no write). A name the Windows code page lacks, or rules that contradict each other, refuse before any change. The Doctor on an Instance (`nvmod doctor --instance <dir> [--masterlist <file>] [--catalog <file>]`) reports `loadorder.missing-master` (error: an active plugin's master is absent, inactive or later), `loadorder.differs-from-loot` (warning with a masterlist, info without: only header masters and the current order then decide), `loadorder.times-out-of-order` (warning: a rebuilt Staging tree loses the times; `sort --apply` rewrites them) and, for NVSE plugin DLLs of the Staging tree, `plugin.game-version-mismatch` and `plugin.xnvse-version-mismatch` against the catalogue's new optional `game_version` and `min_xnvse` fields. A field the catalogue does not record is reported as `plugin.requirements-unknown` (info) and never guessed; the shipped catalogue records none yet. The Doctor compares the required values with the base copy's executable version and the file version of `nvse_1_4.dll` in the base copy, not with anything read from the plugin DLL, whose version struct is still an unverified assumption (see below) | Ticket 19 of nv-linux. The authoritative order is the one in the profile; the times are a derived cache that a rebuilt tree loses |
| Exit codes | 0 success, 1 problems found, 2 refused (nothing changed), 3 verification failure, 4 step failed and rolled back, 5 command line not understood; listed in `nvmod --help` | The ticket's table, extended on 2026-11-14 so scripts and the GUI can tell a refusal from a usage error (nv-linux ticket 37) |
| Staging tree | `nvmod stage --instance <dir> [--profile <name>] [--copy]` builds `staging/<profile>/data/` from the base copy's `Data` folder and the enabled Mods of the profile's `modlist.txt` (MO2 format; a Mod's top-level `meta.ini` is not a game file), every path lowercased, with a manifest `staging/<profile>.json`. The tree is built beside the old one and swapped in only when complete; a failure exits 4 and leaves the old tree. The game executable is not part of it. Where two Mods provide a file the later Mod in the Load order (the one nearer the top of `modlist.txt`) wins. A file that cannot be hard linked is copied (exit 0); `--copy` forces it. The Doctor reports a degraded tree (`stage.degraded`), a missing one (`stage.missing`, info) and Mods with files that differ only in case (`stage.case-collision`; the tree keeps the first in byte order) | Ticket 16 of nv-linux. Hard links share the file with the Mod: a program that edits a staged file in place edits the Mod too (copies avoid it) |
| Mod install and rollback | `nvmod install <archive> --instance <dir> [--profile <name>] [--name <mod name>] [--dry-run] [--answers <file>] [--extract-tool <path>] [--json]` extracts to a scratch folder, places the Mod in `mods/<name>`, adds `+<name>` as the first Mod line of `modlist.txt`, activates the Mod's top-level `.esp`/`.esm` in `plugins.txt` (Windows-1252, a name the code page lacks is refused) and `loadorder.txt` (masters after the last master, other plugins at the end), then runs the staging step. Zip and tar are read in process (`zip`, `tar`, `roxmltree`: all MIT or Apache-2.0); other archives go through `7zz`, `7z`, `7za` or `bsdtar` from `PATH`, or `--extract-tool`. Paths that are absolute or climb with `..`, links, special files, more than 500000 entries or 32 GiB (`--max-extract-bytes`) refuse the archive (exit 2, nothing written). A journal and a backup of the three profile files are written under `<instance>/.nvmod/journal/<id>/` before the first change; a failed step restores them, removes the Mod and exits 4; `nvmod rollback --instance <dir>` undoes the newest install not yet undone (exit 2 when there is none). FOMOD: `fomod/ModuleConfig.xml` is read permissively (UTF-8 or UTF-16). A group is answered without asking only for `SelectAll`, a single `Required` option, a single `Recommended` option, or a single usable option where one must be chosen (`SelectAny` takes its Required and Recommended options); a type that depends on something not visible (a non-plugin file, an unanswered flag) is ambiguous. Any other group exits 1 with the questions (`--json`: `{"status":"questions","questions":[{id,step,group,kind,min,max,options,may_not_apply}]}`); `--answers` takes `{"answers": {"<step>/<group>": ["<option>", ...]}}` and is checked against the group's rule. `gameDependency` and `foseDependency` versions are assumed satisfied (the Doctor checks versions). `NVMOD_FAIL_AT=mod\|lists\|stage` injects a failure for the tests of the automatic rollback | Ticket 18 of nv-linux. Extraction into the system temporary folder keeps a refused or dry-run install free of any write to the Instance. Rolling back restores the three files as they were before the install, so edits made to them afterwards are lost |
| Instance and Profile schema (#25) | The `nvmod-core` crate owns `Instance` (`nvmod-instance.json`) and `Profile` (`profiles/<name>/profile.json`), each with an integer `schema_version`. The schemas are generated with `schemars` and checked in as `schemas/instance.v2.json` and `schemas/profile.v1.json`; a test fails when a file differs from the generated text, and `NVMOD_BLESS=1 cargo test -p nvmod-core` rewrites them. The loaders read the current and the previous version and refuse a newer one (exit 2, with the version found) | The ticket names `instance.v1.json`, but the Instance skeleton already shipped as schema 1, and the owner asked for a version bump with a tested migration, so the Instance schema is v2 and its file is named for the version it describes. The MO2 reader types of `nvmod-formats` were renamed `Mo2Instance` and `Mo2Profile` so no other crate defines an `Instance` or `Profile` | **Yes**: the file naming |
| Schema 1 to 2 migration | Schema 2 renames the version key from `schema` to `schema_version` and adds `target` (`vanilla` or `nv-rs`, default `vanilla`; the Doctor design in `docs/architecture/integration.md` section 8 needs it). A schema 1 file is read as migrated everywhere. Commands that write (`stage`, `sort`, `install`, `install-nv-rs`) rewrite the file on open, after copying the old file to `.nvmod/journal/<id>/backup/` with a journal of kind `migrate`; `nvmod rollback` restores that file byte for byte (and opens the Instance read only, so it never migrates the file it is restoring). `nvmod doctor` and `nvmod rollback` never write | Migrating inside a read-only command would break its promise. There is no separate `nvmod migrate` command: the first write migrates, and nothing is lost because of the backup | No |
| Profile record | `nvmod import-mo2` writes `profile.json` (Mods in `modlist.txt` order with their state, the Load order, the active Plugins) next to the copied MO2 text files. Those text files stay the working copy that `install`, `sort` and `stage` read and write; they do not refresh `profile.json` yet. Folding the text files into the record is a later step | Rewiring every writer onto the record is a larger change than the ticket asks, and a half-done switch would let two copies disagree. Until then `profile.json` is the record as imported | **Yes**: say whether the record should become the working copy next |
